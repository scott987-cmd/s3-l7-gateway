调用方用标准 S3 SDK，但拿不到真实凭证

调用方持有网关签发的虚拟 AK/SK，照常生成标准 SigV4 签名。网关验签通过后剥离旧签名， 用只存在于网关运行态的真实上游凭证重新签名，再访问私网对象存储。 业务代码不需要改造——只改 endpoint、region 和凭证三项。 一应用一把密钥，泄露时秒级吊销单把，不影响其他调用方，也不需要轮换真实凭证。

一、系统架构

四个服务，只有一个对外

只有 nginx 映射宿主端口；authd、creds、sigv4-proxy 都不暴露。全部服务只读根文件系统、cap_drop: ALL、no-new-privileges。

二、双重签名

跨信任边界传的是签名证明，不是密钥

虚拟 SK 和真实 SK 都只在各自受控环境里参与本地 HMAC 计算，两者都不会作为请求参数出现在网络上。

① 客户端发出 · 虚拟凭证签名
PUT /bucket/reports/a.txt HTTP/1.1
Host: s3gw.example.com
Authorization: AWS4-HMAC-SHA256
  Credential=<虚拟AK>/20260728/region/s3/aws4_request,
  SignedHeaders=host;x-amz-content-sha256;x-amz-date,
  Signature=<用虚拟SK计算>
x-amz-date: 20260728T101500Z
x-amz-content-sha256: UNSIGNED-PAYLOAD
# 客户端只知道虚拟凭证，不知道真实凭证存在
② 网关送往上游 · 真实凭证重签
PUT /reports/a.txt HTTP/1.1
Host: bucket.s3-private.example.com
Authorization: AWS4-HMAC-SHA256
  Credential=<真实AK>/20260728/region/s3/aws4_request,
  SignedHeaders=host;x-amz-content-sha256;x-amz-date,
  Signature=<用真实SK重新计算>
x-amz-date: （重新生成）
x-amz-security-token: 客户端夹带的令牌 → 已清除
x-amz-checksum-* / x-amz-trailer → 已清除

入站验签

authd 检查虚拟 AK 是否存在、启用且未过期，再校验 credential scope、300 秒时钟窗口、动态 SignedHeaders、Host 必签，最后做常量时间 HMAC 比对。PUT/POST/DELETE/PATCH 默认启用一次性写请求重放检查。

出站净化

重签前清除客户端的 Authorization、安全令牌、日期、payload hash 和 SDK 的 checksum/trailer 头，避免虚拟签名污染上游、夹带令牌或造成头部混淆。

双重授权

请求必须先通过虚拟凭证验签，再满足真实凭证与桶策略。虚拟凭证不能直接访问对象存储，真实凭证也不会返回客户端——两侧都不可单独打穿。

三、四层 vs 七层

同一个问题的两种解法，取舍点很清晰

「私有对象存储对外接入」有两条路：四层 TCP 透传只搬字节，七层网关理解 S3 语义。下面是能力对照和实测代价——两边都按实际情况说。

维度四层 TCP 透传七层 S3 网关（本方案）
客户端持有的凭证 真实 AK/SK 虚拟 AK/SK 真实凭证不出网关
单个调用方吊销 不支持——换真实凭证会影响所有调用方 秒级 keyctl disable 单把失效，互不影响
调用方审计归因 仅连接级：来源、时长、字节数 对象级 按虚拟 AK 记录方法、对象路径、状态、耗时
按应用/租户隔离 无——所有调用方共用同一份凭证 一应用一把密钥，可设归属、备注、到期
客户端改造 无 改 endpoint / region / 凭证三项，仍用标准 SDK
TLS 端到端不解密 网关内解密并重签（这正是能力的来源）
小对象 QPS
256B 固定响应，并发 4		 11,693 · 0.34 ms 3,951 · 0.97 ms约 1/3
大对象 无应用层缓冲，实测接近网卡上限 有内存特征：256 MiB 并发 16 触发 OOM
上游要求 不解析协议 长尾兼容性最好 需上游支持标准 S3 SigV4
预签名 URL 原样透传 当前不支持（仅请求头 SigV4）
部署形态 nginx stream，两台 ECS 四服务容器编排
需要照看的东西 无证书 · 无凭证 · 无状态 虚拟密钥、业务证书、容器与内存水位

验签成本：小对象 QPS 实测

受控内网对照测试，固定 256 字节响应以隔离上游网络与磁盘影响，只比较三条路径本身的开销。并发 4。

四层 TCP 透传
11,693QPS · 0.34 ms
七层反代（不验签）
10,641QPS · 0.37 ms
完整 S3 网关（本方案）
3,951QPS · 0.97 ms

关键结论：普通 HTTP 解析和反向代理本身几乎不花钱（11,693 → 10,641，只掉 9%）。 真正的成本来自 auth_request 子请求、canonical request 重建和 HMAC 验签。 换句话说，你付的不是「七层」的钱，是「验签 + 治理」的钱。

并发 50 参考QPSp50 延迟
四层 TCP 透传10,7333.48 ms
七层反代（不验签）10,7914.27 ms
完整 S3 网关6,0317.61 ms

并发升高后差距收窄（1/3 → 约 56%）。需要更高小对象 QPS 时，用多实例加负载均衡横向扩展，并在每个实例上单独观察 authd CPU 与 nginx 连接数。

选七层网关，如果其中任意一条成立

  • ✓调用方在信任边界之外，不能持有真实 AK/SK
  • ✓多租户 / 多应用，需要按调用方独立签发、设到期、单独吊销
  • ✓需要回答「哪个调用方在什么时候读写了哪个对象」
  • ✓出事时要能秒级切断某一方，而不是轮换所有人的凭证
  • ✓上游不接受 path-style，需要在中间做寻址转换

选四层透传，如果以上都不需要

  • ✓调用方本来就在可信侧，凭证分发不是问题
  • ✓要的是最高吞吐、最低时延和最少运维动作
  • ✓上游是中小厂商或自建存储，要最广的兼容性
  • ✓需要端到端 TLS，中间不允许存在任何解密点
  • ✓需要预签名 URL 原样透传

→ 四层透传方案仓库

!
两者不是替代关系，取舍点只有一个：调用方在不在你的信任边界内。在边界内，四层更快更省；在边界外，凭证隔离与可吊销性是四层给不了的能力——那不是调参能补上的差距，而是层次决定的。
四、一键部署与验收

一条命令串起配置、预检、部署、健康检查和冒烟

真实 AK/SK 通过环境变量传入，不进 shell history，也不写入交付包。

STEP 01

主机初始化

安装 Docker、Compose 与 aws-cli，可重复执行。

sudo bash scripts/init_host.sh
STEP 02

预检

配置、Docker、上游 DNS 与 TCP 443、端口占用、compose 渲染。不输出 AK/SK 明文。

./scripts/preflight.sh
STEP 03

一键验收

自动串起 configure、preflight、deploy、health 与 smoke，并生成客户端虚拟密钥。

export S3_ACCESS_KEY=... export S3_SECRET_KEY=... ./scripts/acceptance.sh \ S3_REGION=... \ S3_ENDPOINT_HOST=... \ S3_BUCKET_HOST=... \ TEST_BUCKET=...
STEP 04

日常运维

健康、状态、日志、审计、密钥热加载、汇总诊断与支持包。

./scripts/ops.sh health|status ./scripts/ops.sh logs|audit ./scripts/ops.sh doctor|bundle
✓
验收成功的样子。preflight PASS=21 WARN=0 FAIL=0 → smoke PASS=5 WARN=1 FAIL=0 → acceptance passed。那个 WARN 通常是真实上游凭证没有 DeleteObject 权限——这正是最小权限设计在生效。客户明确要求必须能删时设 TEST_REQUIRE_DELETE=1。
五、虚拟密钥与泄露应急

虚拟凭证泄露是有界安全事件

影响范围同时被四件事限制：只是一把密钥、只能经网关生效、背后是最小权限的真实凭证、且绑定单个 bucket。处置不需要轮换所有调用方，更不需要把真实凭证下发给任何应用。

泄露应急闭环 · 五步
# 1. 从审计定位是哪一把虚拟 AK
LINES=500 ./scripts/ops.sh audit

# 2. 秒级禁用并热加载，其他调用方不受影响
./scripts/keyctl.sh disable AKxxxxx --note "suspected credential leak" --reload

# 3. 验证旧凭证立刻返回 403

# 4. 为该应用重新签发独立虚拟凭证
./scripts/keyctl.sh add --owner team-a --note "rotated after incident" \
  --expires 2027-12-31T23:59:59Z --reload

# 5. 生成支持包保留事件证据
./scripts/ops.sh bundle
!
对照一下四层的同一场景。四层透传下调用方持有的是真实 AK/SK，一旦泄露，唯一的处置是轮换真实凭证——而那会同时打断所有调用方，且在轮换完成前泄露方拥有与你完全相同的权限。这就是本方案要买的那份保险。

一应用一把

每把密钥带归属、备注和到期时间，按应用或租户隔离，定期轮换。创建时只显示一次完整 SK，应立即存入秘密管理系统。

禁用优先于删除

disable 保留密钥条目与审计记录，便于事后追溯；变更会追加到 auth/keys_audit.log。

热加载不中断

--reload 原子更新密钥库并发送 SIGHUP，不重启网关、不影响在途请求。

六、纵深防护

不依赖单一鉴权点

任一层配置出错时，后续层仍应继续限制攻击影响。

互联网入口
WAF/负载均衡、IP 白名单、全局限流、Bot 与扫描防护。
传输安全
TLS 1.2/1.3、ECDHE 套件、关闭 session tickets、推荐 HTTPS 回源。
入口收敛
GW_SERVER_NAMES Host 白名单；未知 Host 关闭连接；/healthz 来源白名单。
请求认证
虚拟 SigV4、region/service、时钟窗口、SignedHeaders、Host 必签、常量时间 HMAC。
重放防护
默认对写方法启用进程内一次性签名缓存。
凭证隔离
客户端只持虚拟凭证；真实凭证由 creds 按 static / IMDS / STS 提供。
出站净化
重签前清除客户端 Authorization、安全令牌、日期、payload hash 与 checksum/trailer 头。
最小权限运行
全部服务只读根文件系统、cap_drop: ALL、no-new-privileges；nginx 非 root。
内部隔离
authd、creds、sigv4-proxy 不映射宿主端口，仅 nginx 对外。
审计归因
按虚拟 AK 记录方法、对象路径、状态、上游状态与耗时；不记录完整 query。
!
WAF 可以终止 TLS，但不能改写已签语义。真正会破坏 SigV4 的不是 TLS 卸载，而是改变了客户端签名覆盖的 HTTP 内容：Host、method、对象 key 路径的规范化或重编码、query 的删除重排、签名头的改写，以及对请求体的解压或转码。这几条必须在 WAF 上逐项确认。
